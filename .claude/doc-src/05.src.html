CHAPTER 05 · CI/CD

CI: 검사를 통과한 코드만 main에 들어가게

코드를 바꿀 때마다 기계가 자동으로 검사(CI)하고, 통과한 코드만 main에 합쳐지게 합니다. 06장의 자동 배포는 이 main을 기준으로 움직이므로, 여기서 막은 문제는 운영에 가지 않습니다.

{{MAP:05}}

PR을 만들면 검사가 자동으로 돌고, 모두 통과해야만 main에 머지할 수 있는 저장소를 만든다.

1. CI란

CI(Continuous Integration, 지속적 통합)는 변경을 main에 합치기 전에, 정해진 검사를 사람이 아니라 기계가 매번 같은 방식으로 돌리는 것입니다.

새 메뉴를 가게에 내기 전에 매번 같은 체크리스트로 검수하는 것과 같습니다. "맛은 봤겠지"라고 믿는 대신, 체크리스트를 통과한 것만 메뉴판에 올립니다.
이 장에서 하는 것하지 않는 것 (필요하면 추가)
코드 모양·흔한 실수, 타입, 비밀 값 유출, 운영용 이미지 빌드, 이미지 취약점자동 테스트(단위·화면 조작), 성능 측정 등. 이 예시는 읽기만 하는 단순한 화면이라 넣지 않았습니다

2. GitHub에 올리고 첫 PR 만들기

GitHub에서 빈 저장소를 만들고(README 등은 추가하지 않음), 01~04장의 커밋을 올립니다. 그다음부터는 브랜치를 만들어 PR로 합칩니다.

실행 위치: 저장소 루트

git remote add origin https://github.com/<owner>/<repo>.git
git push -u origin main              # 01~04장의 커밋 (main 보호를 켜기 전에)

git switch -c ci/setup               # 이 장의 작업은 브랜치에서
# … 3~5절의 파일을 추가 …
git add . && git commit -m "ci: lefthook・Dockerfile・GitHub Actions の CI を追加"
git push -u origin ci/setup          # → GitHub 화면에서 "Compare & pull request"로 PR 생성

PR을 만들면 CI가 처음으로 돕니다. 한 번 돈 뒤에 6절의 저장소 설정(main 보호)을 켭니다. 검사 이름이 한 번 등록되어야 필수 검사로 고를 수 있기 때문입니다.

3. 세 겹의 검사

작업은 main이 아니라 브랜치(작업용 사본)에서 하고, PR(Pull Request, "이 변경을 main에 합쳐 달라"는 신청서)로 합칩니다.

앞쪽일수록 빨리 알려 주고, 뒤쪽일수록 건너뛸 수 없습니다. 그래서 같은 검사를 여러 곳에 둡니다.

4. 커밋 직전: lefthook

git commit을 누르는 순간 내 PC에서 자동으로 도는 검사입니다. 규칙은 저장소의 lefthook.yml에 있고, pnpm install 때 각자의 PC에 설치되므로 팀 전원이 같은 검사를 거칩니다.

실행 위치: 저장소 루트

pnpm add -Dw lefthook

그리고 pnpm-workspace.yaml의 allowBuilds에 lefthook: true를 적습니다. 01장에서 "설치할 때 스크립트 실행을 막는다"고 했는데, lefthook은 설치할 때 git에 검사를 등록하는 스크립트가 필요해서 이것만 허용합니다.

검사하는 일
gen-types (07장 뒤에 추가)Strapi 스키마 파일이 커밋에 들어 있으면, 화면용 타입을 다시 만들어 함께 커밋(04장의 pnpm gen:types를 자동으로. DB가 켜져 있어야 함)
biome커밋할 파일의 코드 모양을 고치고, 흔한 실수를 찾는다
gitleaks비밀번호·토큰처럼 보이는 문자열이 있으면 커밋 자체를 막는다

hook은 건너뛸 수 있고(--no-verify) 설치하지 않은 사람에게는 동작하지 않습니다. 그래서 같은 검사를 CI에서 한 번 더 합니다. hook은 빠른 알림, CI는 강제입니다.

5. PR마다: GitHub Actions

.github/workflows/ci.yml에 적어 두면, GitHub이 PR마다 러너(GitHub이 준비하는 새 가상 머신)에서 검사를 돌립니다. 러너는 매번 새로 만들어지므로 "내 PC에서는 되는데"가 통하지 않습니다.

검사 이름하는 일막아 주는 것
checkBiome, 타입 검사, 인프라 코드(CDK) 변환 확인 (CDK는 06장에서 추가)실수·오타, 내 PC에서만 되는 코드
secretsgitleaks로 모든 커밋 기록을 검사과거 커밋에 섞인 비밀 값
image (web) / image (cms)운영과 같은 Docker 이미지를 빌드하고 Trivy로 취약점 검사깨진 빌드, 이미지 안의 알려진 취약점
워크플로에서 지키는 두 가지 보안 원칙 생략 가능
원칙왜
남이 만든 액션은 버전 이름(@v7)이 아니라 커밋 SHA로 고정버전 이름은 다른 코드로 바꿔칠 수 있습니다. 2026년 3월 실제로 유명 액션이 악성 코드로 바뀌어 많은 CI에서 비밀 값이 유출됐습니다
CI에 주는 권한은 기본 읽기만(permissions: contents: read). 검사 결과 업로드에 필요한 쓰기 하나만 해당 job에 추가액션이 악성이어도 저장소를 고칠 수 없습니다

6. Docker 이미지와 취약점 검사

06장에서는 화면과 CMS를 Docker 이미지(앱과 실행에 필요한 것을 묶은 상자)로 AWS에서 실행합니다. CI는 PR마다 그 이미지를 똑같이 빌드해 보고, 안에 든 부품에 알려진 취약점이 없는지 Trivy로 검사합니다. 레시피는 apps/web/Dockerfile, apps/cms/Dockerfile입니다.

2단계로 만든다

1단계에서 설치·빌드, 2단계에는 실행에 필요한 결과물만 옮긴다. 빌드 도구는 운영 이미지에 없다

필요 없는 것은 넣지 않는다

없는 것은 공격에 쓰일 수도, 취약점으로 잡힐 수도 없다

root가 아닌 사용자로 실행

컨테이너가 뚫려도 피해가 작다

비밀 값은 넣지 않는다

실행할 때 환경변수로 넣는다(06장). .dockerignore로 .env도 막는다

취약점이 잡혔을 때 생략 가능

이미지에는 직접 고르지 않은 부품이 수천 개 들어 있고, 새 취약점은 매일 공개됩니다. 이 자료를 만들 때도 처음에 여러 건이 잡혔습니다. 대응 순서는 ① 고친 버전이 있으면 올린다(pnpm-workspace.yaml의 overrides) → ② 실행에 쓰지 않으면 이미지에서 뺀다 → ③ 둘 다 안 되면 이유와 기한을 적고 예외로 둔다, 입니다.

Security 탭의 Code scanning 생략 가능

CI는 Trivy 결과를 SARIF(검사 결과의 표준 형식)로 GitHub에 올립니다. Code scanning은 검사기가 아니라, 올라온 결과를 경고 목록으로 보관하고 "언제 생겼고 언제 고쳐졌는지"를 추적하는 기능입니다. 쓸 수 없는 플랜이면 결과 업로드 단계만 빼면 됩니다.

7. 저장소 설정: "통과해야만 합칠 수 있게"

CI는 결과(✓/✗)를 표시만 합니다. 강제하는 것은 저장소 설정입니다. CI가 한 번 돈 뒤에 설정합니다.

머지 방식: squash만

Settings → General → Pull Requests. PR 안의 커밋 여러 개를 main에 커밋 1개로 합칩니다. PR 제목이 main의 커밋 메시지가 되어 기록이 깔끔합니다.

Ruleset: main 보호

Settings → Rules → Rulesets → New branch ruleset에서 main을 대상으로 만듭니다.

규칙효과
Require a pull request before mergingmain에 직접 push 금지. 반드시 PR을 거친다
Require status checks to pass5절의 검사 4개가 ✓가 아니면 머지 불가
Block force pushes / Restrict deletionsmain의 기록 덮어쓰기·삭제 금지
이 장의 설정은 public 저장소 기준입니다. private 저장소에서는 GitHub 플랜에 따라 Ruleset, Secret scanning, Code scanning을 쓸 수 없을 수 있습니다. 회사 저장소에서 쓸 수 있는 기능을 먼저 확인하세요.

8. 결과: PR 화면

앞으로의 변경은 모두 같은 흐름입니다: 브랜치 → 커밋(lefthook) → push → PR(CI) → squash 머지. 이 장의 커밋은 PR 제목 그대로입니다.
