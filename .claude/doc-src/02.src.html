CHAPTER 02 · 백엔드

스키마: 데이터의 "그릇"을 설계한다

"화면에 무엇을 보여 줄까"에서 거꾸로 생각해 데이터 구조(스키마)를 정하고, Strapi 관리자 화면에서 클릭만으로 만듭니다. 이 장에서는 코드를 쓰지 않습니다.

{{MAP:02}}

가게 정보·메뉴·사이즈·토핑·추가 메뉴를 Strapi 스키마로 만들고, 화면 조작이 파일로 저장되는 것을 확인한다.

1. 먼저 "무엇을 보여 줄지" 적는다

여러분의 사이트로 바꿔서 같은 순서로 생각해 보세요. 이 예시의 메뉴 페이지에는 이런 정보가 필요합니다.

  • 가게 이름, 주소, 영업시간, 정기휴일, 식권 규칙, 가게 사진
  • 메뉴(ラーメン, つけ麺)와 사이즈(小/中/大)별 면 양·가격
  • 무료 토핑(ニンニク・ヤサイ…)과 고를 수 있는 양(ナシ〜マシマシ)
  • 유료 추가(ライス, チャーシュー)와 가격

2. Strapi의 "그릇" 4가지

가게 앞의 메뉴판을 떠올려 보세요. 메뉴판의 정보는 성격에 따라 4가지 그릇으로 나뉩니다.

그릇메뉴판에서는한마디로
① Single Type맨 위의 가게 이름·영업시간하나뿐인 정보
② Collection Typeラーメン 카드, つけ麺 카드…같은 모양으로 여러 개
③ Component카드 안의 「小 800円 / 中 900円」어딘가에 붙어 있는 부품
④ Relation메뉴와 추가 메뉴·토핑을 잇는 선따로 적어 두고 선으로 연결
고르는 기준은 3가지 질문입니다. 하나뿐인가? → Single Type. 여러 개를 목록으로 관리하나? → Collection Type. 어딘가에 붙어 있나, 여러 곳에서 공유하나? → 붙어 있으면 Component, 공유하면 Collection으로 따로 만들고 Relation으로 연결.
왜 사이즈는 부품이고, 추가 메뉴는 선(Relation)인가요? 생략 가능

ラーメン의 小는 800円, つけ麺의 小는 900円처럼 사이즈 가격은 메뉴마다 달라서 공유할 것이 없습니다 → 각 카드에 붙는 부품. 반대로 「ライス ＋100円」은 어느 메뉴에 붙든 같습니다. 한 곳에 적고 선으로 이으면, 가격이 오를 때 한 곳만 고치면 됩니다.

여러분의 사이트라면SingleCollectionComponentRelation
회사 홈페이지회사 소개공지사항, 직원직원의 SNS 링크공지 → 작성한 직원
블로그블로그 소개글, 태그글 안의 관련 링크글 ↔ 태그

3. 관리자 화면에서 만든다

실행 위치: 저장소 루트

pnpm dev:db
pnpm dev:cms   # → http://localhost:1337/admin

처음 접속하면 관리자 등록 화면이 나옵니다(로컬 전용 계정). 등록 후 왼쪽 메뉴의 Content-Type Builder에서 그릇을 만들고 필드를 추가합니다.

이번에 만든 그릇과 필드입니다. 필수 여부 등은 필드의 ADVANCED SETTINGS에서 정합니다.

그릇필드
Single Shopname(필수), catchphrase, address, closedDays, businessHours·ticketRule(여러 줄), photo(사진)
Component menu.sizelabel(small / medium / large 중 선택, 필수), noodleGrams, price(필수)
Component menu.levellabel(ナシ・フツウ… 필수)
Collection Toppingname(필수), description, levels(menu.level 여러 개)
Collection Extraname(필수), price(필수), photo (07장에서 soldOut 추가)
Collection Menuname(필수), description, photo, sizes(menu.size 여러 개), extras·toppings(다대다 Relation)

헷갈리기 쉬운 점

① 선택지(Enumeration)의 값은 영문으로. 小를 그대로 넣으면 오류가 납니다. 값은 프로그램이 쓰는 식별자이고, "小" 표시는 화면(04장)에서 붙입니다.

② 부품을 여러 개 붙이려면 Repeatable. 메뉴 하나에 사이즈 3개, 토핑 하나에 양 4개.

③ 선(Relation)의 종류는 문장으로 확인. 아이콘을 고르면 아래에 의미가 문장으로 나옵니다.

Content-Type Builder는 로컬(개발 모드)에서만 쓸 수 있습니다. 운영에서는 잠겨 있습니다. 스키마는 로컬에서 바꾸고 Git으로 배포합니다.

4. 저장하면 "파일"이 된다

왼쪽 위의 Save를 누르면 Strapi가 재시작하면서 설계도 파일을 씁니다.

apps/cms/src/api/<그릇>/content-types/<그릇>/schema.json

그릇의 설계도. 화면에서 고른 필드가 그대로 적힌다

apps/cms/src/api/<그릇>/controllers·routes·services

API를 만드는 코드. 자동 생성이라 손대지 않는다

apps/cms/src/components/menu/*.json

부품(Component)의 설계도

schema.json 안을 보기 생략 가능 {{EX:apps/cms/src/api/menu/content-types/menu/schema.json:26:42}}

화면에서 고른 "부품 여러 개", "다대다 선"이 그대로 JSON으로 적혀 있습니다.

이 연수의 핵심 하나. 이 설계도 파일(스키마)은 Git → PR → 자동 배포를 거쳐 운영에 가고, 운영 Strapi가 기동할 때 테이블을 만듭니다. 하지만 관리자 화면에서 입력한 데이터는 각 환경의 DB에만 있고 배포되지 않습니다.
