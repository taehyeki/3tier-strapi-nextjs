CHAPTER 06 · CI/CD

CD: 머지하면 AWS에 자동으로 반영되게

main이 바뀌면 자동으로 운영(AWS)에 반영되게 하고, 첫 배포 뒤의 운영 초기 설정까지 합니다. AWS 구성은 여러분의 설계를 쓰면 되므로, 여기서는 배포의 흐름과 "설정 값이 어디서 오는가"를 중심으로 봅니다.

{{MAP:06}}

main에 머지하면 앱 이미지가 한 번 만들어져 보관되고, 그 이미지로 AWS가 갱신된다. 운영 관리자 등록·데이터 입력·API 토큰 설정까지 마쳐 운영 사이트가 뜬다.

1. 전체 흐름

운영에 보내는 앱 이미지는 main에서 한 번만 만들고, 검사를 통과한 그 이미지를 그대로 배포합니다. 이미지에는 커밋 번호(SHA)가 붙어서, 운영에서 어느 커밋이 돌고 있는지 언제든 알 수 있습니다.
PR에서 만든 이미지를 그대로 쓰지 않는 이유 생략 가능

PR 단계의 코드는 아직 머지 전이라, 운영 저장소에 올릴 권한을 주지 않습니다. 또 squash 머지는 main에 새 커밋을 만들기 때문에, 운영 이미지는 그 커밋에서 만들어야 기록이 정확합니다. PR의 빌드는 "머지해도 되나"의 검사, main의 빌드는 "운영에 보낼 결과물"입니다. 둘은 같은 빌드 단계를 씁니다.

2. AWS 구성은 "스택" 3개로 나눴다

AWS 구성은 CDK(AWS 구성을 TypeScript 코드로 적는 도구)로 infra/에 적었습니다. 전체 그림은 00장을 보세요. 코드는 배포하는 단위(스택)로 셋으로 나눴습니다.

① Foundation (토대)

이미지 보관소(ECR), GitHub가 AWS에 들어올 때 쓰는 역할(IAM). 사람이 처음 한 번 만든다. 자동 배포가 쓰는 것이라 자동 배포로는 만들 수 없기 때문

② Data (데이터)

네트워크(VPC), DB(Aurora), 사진(S3), 비밀 값(Secrets Manager). 지우면 되돌릴 수 없는 것이라 삭제 보호를 켠다

③ App (앱)

입구(CloudFront, ALB), 컨테이너(ECS의 web·cms). 언제 지우고 다시 만들어도 되는 것. 배포 때마다 바뀌는 쪽

왜 이렇게 나누나요? 생략 가능

"데이터가 있는 것과 없는 것을 다른 스택으로"는 CDK 공식 모범 사례입니다(AWS CDK Best practices). 앱 쪽을 몇 번 다시 만들어도 DB와 사진은 안전합니다. 코드: infra/bin/(스택 조립), infra/lib/(층별 파일).

3. 처음 한 번만 하는 준비

자동 배포가 돌기 전에 있어야 하는 것들입니다. 사람이 한 번만 합니다.

① CDK 준비계정·리전당 1회cdk bootstrap
→
② 토대 스택이미지 보관소 + 역할내 PC에서 배포
→
③ GitHub 설정Environment 1개 + 시크릿 2개②의 출력 값을 등록

실행 위치: 저장소 루트 (AWS 자격 증명이 있는 터미널)

pnpm -F infra exec cdk bootstrap aws://<계정 ID>/ap-northeast-1
pnpm -F infra foundation deploy \
  -c githubSubjectPrefix="$(gh api repos/<owner>/<repo>/actions/oidc/customization/sub --jq .sub_claim_prefix)"

②가 끝나면 역할 이름(ARN) 2개가 출력됩니다. GitHub에 등록합니다.

GitHub 시크릿등록하는 곳쓰는 곳
AWS_IMAGE_PUSH_ROLE_ARNSettings → Secrets and variables → Actions이미지를 보관소에 올릴 때
AWS_DEPLOY_ROLE_ARNSettings → Environments → 3tier-prod(새로 만듦)AWS에 배포할 때

GitHub가 AWS에 들어가는 방법 (OIDC)

GitHub에 AWS의 열쇠(액세스 키)를 맡기지 않습니다. 대신 실행할 때마다 GitHub가 "이 저장소의, 이 작업입니다"라는 신분증을 발급하고, AWS는 신분증이 조건과 맞을 때만 1시간짜리 방문증을 내줍니다. 오래 쓰는 열쇠가 어디에도 없으니 도둑맞을 것도 없습니다.
역할누가 쓸 수 있나할 수 있는 것
이미지 올리기main 브랜치의 작업만이미지 보관소에 올리기만
배포Environment 3tier-prod의 작업만CDK로 배포하기만

PR의 작업은 어느 역할도 쓸 수 없습니다. 머지 전 코드가 운영을 건드릴 수 없다는 뜻입니다.

githubSubjectPrefix를 API로 받는 이유 생략 가능

2026-07-15 이후에 만든 저장소는 신분증의 저장소 표기가 소유자@ID/저장소@ID처럼 숫자 ID가 붙은 형식입니다(저장소를 지운 뒤 누가 같은 이름으로 만들어도 구별되도록). 추측해서 적으면 Not authorized to perform sts:AssumeRoleWithWebIdentity로 실패합니다(이 자료를 만들 때 실제로 겪음). GitHub API가 그 저장소의 실제 형식을 알려 주므로 그대로 넣습니다.

배포 전에 사람의 승인을 받고 싶다면 생략 가능

Environment 3tier-prod에서 Required reviewers(승인자)를 정하면, 배포 직전에 승인 대기로 멈춥니다. Deployment branches를 main으로 제한하면 다른 브랜치에서는 배포할 수 없습니다. 이 예시는 승인 없이 "머지 = 배포"로 했습니다.

4. 배포 워크플로가 하는 일

.github/workflows/deploy.yml. main에 머지되고 앱·인프라 파일이 바뀌었을 때 돕니다(문서만 바뀐 머지는 배포하지 않음).

단계하는 일걸리는 시간 (이 예시)
publish (web·cms 동시)이미지를 빌드 → 취약점 검사(05장과 같은 단계) → 보관소(ECR)에 올림. 태그 = 커밋 SHA약 5분
deploycdk deploy: 인프라에 바뀐 것이 있으면 반영하고, 컨테이너가 새 이미지를 쓰게 한다. 빌드는 하지 않는다평소 약 5분 (첫 배포는 DB·CloudFront를 만드느라 약 25분)
ECS 교체새 컨테이너가 정상인 것을 확인한 뒤 옛 것을 내린다. 새 버전이 뜨지 않으면 자동으로 옛 버전으로배포에 포함

5. 설정 값은 어디서 오나

앱은 로컬과 운영에서 같은 코드이고, 같은 이름의 환경변수를 읽습니다(01장). 값을 넣는 곳만 다릅니다.

종류예로컬운영
비밀 아닌 값접속할 주소, 사진 버킷 이름.env / .env.localAWS 구성 코드(CDK)가 채워서 컨테이너에 넣음
비밀 값DB 비밀번호, Strapi 키, API 토큰.env / .env.localSecrets Manager에 보관 → 컨테이너가 시작될 때 ECS가 꺼내 넣음
운영의 비밀 값은 AWS가 무작위로 만듭니다(DB 비밀번호, Strapi 키). 사람이 값을 보거나 옮길 일이 없고, GitHub에는 앱의 비밀 값이 하나도 없습니다. 예외는 API 토큰 하나로, 운영 Strapi가 떠야 발급할 수 있어 첫 배포 뒤에 넣습니다(7절).

6. 운영에서만 쓰는 Strapi 설정

apps/cms/config/env/production/의 파일은 운영에서만 기본 설정 위에 덮어씁니다. 로컬 개발에는 영향이 없습니다.

설정왜 필요한가
사진을 S3에 저장컨테이너의 디스크는 재시작하면 사라진다. S3 접근은 코드에 키를 적지 않고 AWS 역할로
관리자 화면의 공개 주소, "HTTPS로 왔다"를 Strapi에 알림CloudFront → ALB를 거쳐 들어오므로. 없으면 관리자 로그인 쿠키가 안전하게 설정되지 않는다
관리자 화면이 S3 사진을 표시하도록 허용기본 설정은 자기 주소의 이미지만 허용한다
DB 접속 암호화 + 상대 확인운영 DB는 암호화되지 않은 접속을 거부한다. AWS 공식 인증서를 이미지에 넣어 "진짜 AWS의 DB인지" 확인한다

전체: apps/cms/config/env/production/, apps/cms/src/middlewares/cloudfront-proto.ts, apps/cms/Dockerfile. web은 상태 확인용 /healthz만 추가했습니다.

8. 배포가 실패했을 때

실패한 배포는 자동으로 이전 상태로 돌아가므로 사이트는 그대로입니다. 운영을 직접 고치지 않고, 코드를 고쳐 같은 흐름(PR → 머지)으로 다시 보냅니다. 이 자료를 만들 때도 첫 배포에서 두 번 실패했습니다.

증상 (어디서 보나)원인
publish가 Not authorized to perform sts:AssumeRoleWithWebIdentity (Actions 로그)역할의 조건과 GitHub 신분증의 형식이 다름(3절)
deploy가 Invalid rule description (CloudFormation 콘솔 → 스택 → 이벤트)AWS에 보낸 설명 문구에 쓸 수 없는 문자(>). AWS로 보내는 이름·설명은 영문으로
deploy가 오래 걸린 뒤 실패 (ECS 콘솔 → 서비스 → 이벤트·로그)새 컨테이너가 상태 확인을 통과하지 못함(설정 값, DB 접속 등). CloudWatch Logs의 앱 로그를 본다

9. 비용과 정리

이 구성은 켜 두기만 해도 요금이 나옵니다(도쿄 리전, 2026-09 기준 대략 월 $150, 하루 $5). 큰 항목은 DB(Aurora, 약 $55), NAT Gateway(약 $49), 컨테이너(약 $27), ALB(약 $18)입니다.

지우는 방법 (앱 → 데이터 → 토대 순서) 생략 가능

실행 위치: 저장소 루트 (AWS 자격 증명이 있는 터미널)

pnpm -F infra exec cdk destroy ThreeTierApp -c imageTag=-
# 데이터 스택은 삭제 보호를 끈 뒤에 지운다 (DB 는 마지막 스냅샷이 남는다)
aws cloudformation update-termination-protection --no-enable-termination-protection --stack-name ThreeTierData
pnpm -F infra exec cdk destroy ThreeTierData -c imageTag=-
pnpm -F infra foundation destroy -c githubSubjectPrefix=-

남은 DB 스냅샷은 필요 없으면 RDS 콘솔에서 지웁니다.
