CHAPTER 01

로컬 환경: 내 PC에 3층을 작게 만든다

빈 폴더에서 시작해 화면(Next.js), CMS(Strapi), DB(PostgreSQL)가 내 PC에서 모두 뜨는 상태까지 만듭니다. 대부분은 생성 도구가 만들어 주므로, 직접 하는 일은 많지 않습니다.

{{MAP:01}}

http://localhost:3000(화면)과 http://localhost:1337/admin(CMS 관리자 화면)이 열리고, CMS가 DB에 연결된 상태를 만든다.

1. 무엇을 만드나

세 가지를 저장소(폴더) 하나에 둡니다. 이런 구성을 모노레포라고 합니다. "CMS의 데이터 구조 변경 + 화면 변경"을 한 번에 검사하고 배포할 수 있어서 편합니다.

📁 이 장이 끝나면
3tier-strapi-nextjs/
├── apps/
│   ├── web/      프론트 Next.js  (create-next-app 이 생성)
│   └── cms/      백엔드 Strapi   (create-strapi 가 생성)
├── compose.yaml  DB    PostgreSQL 컨테이너 설정
└── 설정 파일 몇 개 (버전 고정, 명령 모음, 코드 검사 규칙)

2. 도구 준비

3. 저장소 뼈대

실행 위치: 작업용 폴더

mkdir 3tier-strapi-nextjs && cd 3tier-strapi-nextjs
git init -b main
mkdir apps

루트에 설정 파일을 둡니다. 내용은 저장소의 파일을 참고하세요. 각 파일이 하는 일은 이렇습니다.

package.json

자주 쓰는 명령 모음(pnpm dev:cms 등)과 pnpm 버전 고정

pnpm-workspace.yaml

apps/ 아래 앱들을 하나로 묶는다 + 설치할 때의 보안 설정

.nvmrc

Node 버전 고정(24). 모두가 같은 버전을 쓴다

.gitignore

Git에 올리지 않을 것: 비밀 값(.env), 설치 결과 등

.editorconfig 생략 가능

에디터가 달라도 들여쓰기·줄바꿈을 같게

pnpm이 막아 주는 두 가지 (공급망 공격 방지) 생략 가능

누군가 유명 패키지에 악성 코드를 섞어 공개하는 공격(공급망 공격)이 실제로 일어납니다. pnpm 12는 기본으로 ① 설치할 때 패키지의 스크립트 실행을 막고(허용한 것만 pnpm-workspace.yaml의 allowBuilds에), ② 공개된 지 하루가 안 된 버전은 설치하지 않습니다. 새 패키지를 넣다가 ERR_PNPM_IGNORED_BUILDS가 나오면 allowBuilds에 그 패키지를 적고 허용 여부를 정합니다.

4. DB: 컨테이너로 띄운다 DB

DB는 PC에 설치하지 않고 Docker 컨테이너로 실행합니다. 누구의 PC에서든 같은 버전이 뜨고, 필요 없으면 통째로 지울 수 있습니다. 설정은 compose.yaml 하나입니다.

설정값의미
이미지postgres:17-alpine운영(Aurora)과 같은 메이저 버전
DB 이름·사용자·비밀번호모두 strapi로컬 전용 값. 운영 비밀번호는 AWS가 무작위로 만든다(06장)
포트5432PC에서 이 번호로 접속
볼륨db-data컨테이너를 지워도 데이터가 남는다

실행 위치: 저장소 루트

pnpm dev:db
docker compose ps

STATUS에 (healthy)가 표시됩니다.

5. CMS: Strapi 설치 백엔드

실행 위치: 저장소 루트

npx create-strapi@latest apps/cms \
  --ts --use-pnpm --install --no-run --skip-cloud --no-example --no-git-init \
  --dbclient postgres --dbhost 127.0.0.1 --dbport 5432 \
  --dbname strapi --dbusername strapi --dbpassword strapi --dbssl false

TypeScript로, 예제 데이터 없이, 4절의 DB에 연결하도록 만듭니다. 이어서 모노레포에 맞게 조금 정리합니다.

실행 위치: apps/cms

# Strapi Cloud(유료 호스팅)용이라 불필요 (이 두 줄은 생략해도 동작합니다)
pnpm remove @strapi/plugin-cloud
npm pkg delete scripts.deploy scripts.upgrade "scripts.upgrade:dry"
# pnpm 설정은 루트 하나로
npm pkg delete pnpm
# 타입 검사 명령 (05장의 자동 검사가 쓴다)
npm pkg set scripts.typecheck="tsc --noEmit"
pnpm add -D @types/node@^24

설정 값은 "환경변수"로 받는다

Strapi의 설정 파일은 DB 주소나 비밀 값을 직접 적지 않고, 환경변수라는 이름표로 읽습니다(예: DATABASE_HOST). 값을 넣는 곳만 환경마다 다릅니다.

로컬apps/cms/.env 파일생성 도구가 만든다. 비밀 값이 들어 있어 Git에 올리지 않음
→
같은 이름으로 읽는다env("DATABASE_HOST")코드는 로컬·운영 모두 같다
←
운영(AWS)Secrets Manager 등ECS가 컨테이너에 넣어 준다(06장)

대신 "어떤 값이 필요한지"만 적은 apps/cms/.env.example을 Git에 올립니다(값은 가짜).

각 비밀 값은 무엇에 쓰이나요? 생략 가능
변수쓰이는 곳값이 바뀌면
APP_KEYS로그인 세션에 서명(위조 방지 도장)로그인 세션이 무효
ADMIN_JWT_SECRET관리자 로그인 토큰에 서명관리자가 다시 로그인
API_TOKEN_SALTAPI 토큰(03장)을 저장할 때 섞는 값발급한 API 토큰이 모두 무효
ENCRYPTION_KEY발급한 토큰을 관리자 화면에서 다시 볼 수 있게 암호화저장된 토큰을 표시할 수 없음
TRANSFER_TOKEN_SALT, JWT_SECRET이번에는 쓰지 않는 기능용—

실행 위치: 저장소 루트

pnpm install
pnpm dev:cms

http://localhost:1337/admin에서 관리자 등록 화면이 열립니다(등록은 02장에서).

6. 화면: Next.js 설치 프론트

실행 위치: 저장소 루트

npx create-next-app@latest apps/web \
  --ts --tailwind --biome --app --src-dir --import-alias '@/*' \
  --use-pnpm --skip-install --disable-git

중요한 것은 --app(App Router)입니다. 서버에서만 실행되는 코드를 쓸 수 있어서, 04장에서 API 토큰을 브라우저에 숨길 수 있습니다. 이어서 모노레포에 맞게 정리합니다.

실행 위치: 저장소 루트

rm apps/web/pnpm-workspace.yaml     # pnpm 설정은 루트 하나로
mv apps/web/biome.json biome.json   # 코드 검사 규칙을 루트로 옮겨 web·cms 공통으로
cd apps/web
npm pkg delete packageManager scripts.lint scripts.format "devDependencies.@biomejs/biome"
npm pkg set scripts.typecheck="next typegen && tsc --noEmit"
cd ../..
pnpm add -D @types/node@^24 --filter web
pnpm install
pnpm dev:web

7. 코드 검사 도구(Biome)와 첫 커밋

Biome은 코드 모양을 통일(포맷)하고 흔한 실수를 찾아(린트) 줍니다. 루트의 biome.json 하나로 모든 앱에 같은 규칙을 적용합니다. 규칙은 기본 추천 세트(recommended)를 쓰고, 자동 생성 파일·문서 등은 검사에서 뺍니다. 전체: biome.json

실행 위치: 저장소 루트

pnpm install
pnpm format      # 전체 코드를 규칙에 맞게 자동 수정
pnpm lint        # 검사만
git add .
git commit -m "chore: ローカル開発環境を構築"

Strapi가 만든 파일에서 경고(warning)가 몇 개 나오는데, 생성기의 코드 스타일 때문이라 괜찮습니다. error가 없으면 됩니다.

커밋 메시지 규칙 생략 가능

종류: 내용 형식(Conventional Commits)을 씁니다. 종류는 feat(기능), fix(수정), chore(설정), docs(문서) 정도면 충분합니다. 내용은 팀이 읽는 언어로 씁니다(이 예시는 일본어).
