1. 何を作ったか

フロントエンドNext.jsお客様に見せる画面をサーバーで作る。API トークンはサーバーだけに
→
バックエンドStrapi管理画面でデータ構造を作ると API が自動でできる
→
DBPostgreSQLデータを保管する。写真は S3 に

自分で書いたコードは、画面(page.tsx など数ファイル)と設定ファイルがほとんどです。データ構造と API は Strapi の管理画面でクリックして作りました。バックエンドを1から書かなくても、こうして役割を分けた構成を作れます。

4. 人がやること、自動でやってくれること

人がやること自動でやってくれること
最初の1回道具のインストール、リポジトリ設定(Ruleset)、AWS の土台(イメージ保管庫・ロール)、GitHub シークレット2つ—
機能を変えるたびローカルで作って確認 → PR → マージコミット直前の検査・型生成、PR の検査、イメージのビルド・検査、AWS へのデプロイ、無停止での切り替え
本番でデータの入力・公開(初回デプロイ直後は管理者登録・API トークンも)—

5. どこにでも通じる5つの原則

秘密の値はコードの外に

ローカルは .env(Git 除外)、本番は Secrets Manager。コード・イメージ・GitHub には残さない

通行証はサーバーだけに

API トークンは画面を作るサーバーだけが持つ。ブラウザには結果(HTML)だけ

権限は必要な分だけ

トークンは読み取りだけ、CI は読み取りだけ、GitHub の AWS ロールはやることが1つだけ

検査を通過したものだけ main に

人の記憶ではなく、機械の検査とリポジトリのルールで守る

同じコードをすべての環境で

ローカルと本番はコードが同じで、環境変数で入れる値だけが違う

6. 皆さんがやること

ここまでラーメン店を例に、開発から本番デプロイまでの全体の流れを見てきました。これを参考にして、皆さんが構想したインフラを土台に、自分だけの CMS サイトを開発してください。

  1. テーマを決めて「画面に見せる情報」を書き出す → 3つの質問で入れ物を選ぶ(02章)
  2. ローカル環境を作る: 1つのリポジトリに画面・CMS、DB はコンテナ(01章)。皆さんの設計が MySQL なら、Strapi を MySQL で作っても構いません
  3. スキーマ → データ → トークン(02・03章)
  4. 画面を作る: 受け取った値をどこに入れるかから(04章)。デザインは自由
  5. GitHub と CI をつなげる(05章)。会社のリポジトリで使える機能を先に確認
  6. 皆さんのインフラにデプロイする(06章)。00章の「WordPress 前提の設計との違い」の表を見て設計に反映します: アプリ2つ、入口の振り分け、アプリ同士の通信、写真は S3
  7. 小さな変更を本番まで送ってみる(07章)。流れが一周すれば完成です
行き詰まったらこのリポジトリを見てください。資料に出てくる設定はすべて、実際に動いたファイルそのままです: 画面 apps/web/、CMS apps/cms/、自動検査 lefthook.yml・.github/workflows/ci.yml、自動デプロイ .github/workflows/deploy.yml、AWS 構成 infra/。
