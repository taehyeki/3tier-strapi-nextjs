CD: マージすると AWS に自動で反映されるようにする

main が変わると自動で本番(AWS)に反映されるようにし、初回デプロイのあとの本番初期設定まで行います。AWS の構成は皆さんの設計を使えばよいので、ここではデプロイの流れと「設定値がどこから来るか」を中心に見ます。

main にマージするとアプリのイメージが一度作られて保管され、そのイメージで AWS が更新される。本番の管理者登録・データ入力・API トークン設定まで終えて本番サイトを立ち上げる。

1. なぜ自動デプロイ(CD)が必要か

05章までで、「main には検査を通ったコードしかない」状態を作りました。ではそのコードを、誰がどうやって AWS に反映するのでしょうか。手でやる方法と比べてみます。

手でデプロイ自動デプロイ(CD)
やり方その都度 AWS コンソールを開き、新しいイメージを作って手順通りに反映main にマージした瞬間、決まった手順が毎回同じ順で実行される
手順を忘れたら本番が古いまま、または途中の状態で止まる手順自体がコードなので、抜け漏れが起きない
何が本番で動いているかデプロイした人の記憶やメモ頼み本番のイメージにコミット番号が付くので、いつでも確認できる(4節)
複数人での作業誰かの PC の環境や手順の癖に依存誰がマージしても同じ手順が走る
CI(05章)が「メニューに出す前の検品」なら、CD は「検品を通った料理を、決まった手順で毎回同じように客席まで運ぶ仕組み」です。運ぶ人によって手順が変わったり、運ぶのを忘れたりしないようにします。

これがCD(Continuous Delivery/Deployment、継続的デリバリー/デプロイ)です。承認を挟めば Continuous Delivery、挟まなければ Continuous Deployment と呼ばれますが、どちらも「main の変更を、人手を介さず本番まで届ける仕組み」という点は同じです。

2. 全体の流れ

原則は1つです。普段の AWS への変更は自動デプロイだけで行います。人が AWS を直接操作するのは、最初の1回だけの準備(4節)、本番初期設定の2行(8節)、後片付け(10節)だけです。

本番に送るアプリのイメージは main で一度だけ作り、検査を通過したそのイメージをそのままデプロイします。イメージにはコミット番号(SHA)が付くので、本番でどのコミットが動いているか、いつでもわかります。
PR で作ったイメージをそのまま使わない理由 省略可

PR 段階のコードはまだマージ前なので、本番用の保管庫に上げる権限を与えません。また squash マージは main に新しいコミットを作るため、本番用イメージはそのコミットから作らないと記録が正確になりません。PR のビルドは「マージしてよいか」の検査、main のビルドは「本番に送る成果物」です。両方とも同じビルド手順を使います。

3. AWS 構成は「スタック」3つに分けた

AWS の構成はCDK(AWS の構成を TypeScript コードで書く道具)で infra/ に書きました。全体像は00章を見てください。コードはデプロイする単位(スタック)で3つに分けました。

① Foundation(土台)

イメージ保管庫(ECR)、GitHub が AWS に入るときのロール(IAM)。人が最初に1回だけ作る。自動デプロイが使うものなので、自動デプロイ自身では作れないため

② Data(データ)

ネットワーク(VPC)、DB(Aurora)、写真(S3)、秘密の値(Secrets Manager)。消すと元に戻せないものなので削除保護を有効にする

③ App(アプリ)

入口(CloudFront, ALB)、コンテナ(ECS の web・cms)。いつ消して作り直してもよいもの。デプロイのたびに変わる側

なぜこう分けるのですか? 省略可

「データを持つものと持たないものを別スタックに」は CDK の公式ベストプラクティスです(AWS CDK Best practices)。アプリ側を何度作り直しても DB と写真は安全です。コード: infra/bin/(スタックの組み立て)、infra/lib/(層ごとのファイル)。

4. 最初の1回だけ行う準備

自動デプロイが動く前に必要なものです。人が1回だけ行います。

会社の共有アカウントなら、まず管理者に確認してください: ① CDK の準備(bootstrap)は済んでいるか ② GitHub OIDC プロバイダー(アカウントに1つ)はあるか ③ 自分の権限で IAM ロールを作れるか。プロバイダーがなければ、土台スタックのデプロイに -c useExistingOidcProvider=false を付ければ一緒に作ります。複数人が同じアカウントにこの例をデプロイすると名前が衝突するので、スタック名(infra/bin/*.ts)とイメージ保管庫名(infra/lib/shared.ts, deploy.yml)に自分の接頭辞を付けます。
① CDK の準備アカウント・リージョンごとに1回cdk bootstrap
→
② 土台スタックイメージ保管庫 + ロール自分の PC からデプロイ
→
③ GitHub 設定Environment 1つ + シークレット2つ②の出力値を登録

実行場所: リポジトリのルート(AWS 認証情報のあるターミナル)

pnpm -F infra exec cdk bootstrap aws://<アカウント ID>/ap-northeast-1
pnpm -F infra foundation deploy \
  -c githubSubjectPrefix="$(gh api repos/<owner>/<repo>/actions/oidc/customization/sub --jq .sub_claim_prefix)"

②が終わるとロール名(ARN)が2つ出力されます。GitHub に登録します。

GitHub シークレット登録する場所使う場所
AWS_IMAGE_PUSH_ROLE_ARNSettings → Secrets and variables → Actionsイメージを保管庫に上げるとき
AWS_DEPLOY_ROLE_ARNSettings → Environments → 3tier-prod(新規作成)AWS にデプロイするとき

Environment 3tier-prod を作るとき、Deployment branches and tags を「Selected」→ main のみに制限します。これがないと、書き込み権限を持つ人が別のブランチでこの環境を指定し、デプロイ用ロールを借りられてしまいます。必ず設定してください。

GitHub が AWS に入る方法(OIDC)

GitHub に AWS の鍵(アクセスキー)を預けません。代わりに実行のたびに、GitHub が「このリポジトリの、この作業です」という身分証を発行し、AWS は身分証が条件に合うときだけ1時間だけの訪問証を渡します。長く使う鍵がどこにもないので、盗まれるものがありません。
ロール誰が使えるかできること
イメージを上げるmain ブランチの作業だけイメージ保管庫に上げるだけ
デプロイEnvironment 3tier-prod の作業だけCDK でデプロイするだけ

PR の作業はどちらのロールも使えず、環境は main でしか使えません。マージ前のコードが本番に触れないということです。

githubSubjectPrefix を API で受け取る理由 省略可

2026-07-15 以降に作ったリポジトリは、身分証のリポジトリ表記が owner@ID/repo@ID のように数字の ID が付いた形式です(リポジトリを削除したあと誰かが同じ名前で作っても区別できるように)。推測して書くと Not authorized to perform sts:AssumeRoleWithWebIdentity で失敗します(この資料を作るときに実際に遭遇しました)。GitHub API がそのリポジトリの実際の形式を教えてくれるので、そのまま入れます。

デプロイ前に人の承認を受けたい場合 省略可

Environment 3tier-prod でRequired reviewers(承認者)を設定すると、デプロイ直前に承認待ちで止まります。この例では承認なしで「マージ = デプロイ」としました。

5. デプロイワークフローがやること

.github/workflows/deploy.yml。main にマージされ、アプリ・インフラのファイルが変わったときに動きます(ドキュメントだけ変わったマージはデプロイしません)。

段階やることかかる時間(この例)
publish(web・cms 同時)イメージをビルド → 脆弱性検査(05章と同じ手順)→ 保管庫(ECR)に上げる。タグ = コミット SHA約5分
deploycdk deploy: インフラに変更があれば反映し、コンテナが新しいイメージを使うようにする。ビルドはしない普段は約5分(初回デプロイは DB・CloudFront を作るため約25分)
ECS の切り替え新しいコンテナが正常なことを確認してから古いものを落とす。新バージョンが立ち上がらなければ自動で旧バージョンに戻すデプロイに含まれる

皆さんのインフラが CDK でないなら

コンソールで作った場合や EC2 で設計した場合も、流れは同じです。publish(イメージのビルド・検査・保管)はそのまま使い、deploy の最後の1段階だけ変えます。

皆さんの構成deploy でやることロールに必要な権限
ECS(コンソールで作成)新しいイメージタグでタスク定義を更新し、サービスを切り替える(公式アクション aws-actions/amazon-ecs-deploy-task-definition、または aws ecs update-service)ECS のタスク定義・サービス更新
EC2サーバーに「新しいイメージを取得して再起動しろ」という命令を送る(SSM Run Command で docker pull → 再起動)SSM コマンドの実行

GitHub が OIDC でロールを借りる部分(4節)は、どの構成でも同じです。ロールの権限だけ上の表に合わせて絞ります。

6. 設定値はどこから来るか

アプリはローカルと本番で同じコードで、同じ名前の環境変数を読みます(01章)。値を入れる場所だけが違います。

種類例ローカル本番
秘密でない値接続先アドレス、写真バケット名.env / .env.localAWS 構成コード(CDK)が埋めてコンテナに渡す
秘密の値DB パスワード、Strapi の鍵、API トークン.env / .env.localSecrets Manager に保管 → コンテナ起動時に ECS が取り出して渡す
本番の秘密の値はAWS がランダムに作ります(DB パスワード、Strapi の鍵)。人が値を見たり運んだりすることはなく、GitHub にはアプリの秘密の値が1つもありません。例外は API トークンだけで、本番の Strapi が起動していないと発行できないため、初回デプロイのあとに入れます(8節)。

7. 本番でだけ使う Strapi の設定

apps/cms/config/env/production/ のファイルは、本番でだけ既定の設定の上に上書きします。ローカル開発には影響しません。

設定なぜ必要か
写真を S3 に保存コンテナのディスクは再起動すると消える。S3 へのアクセスはコードに鍵を書かず AWS のロールで行う
管理画面の公開アドレス、「HTTPS で来た」を Strapi に伝えるCloudFront → ALB を経由して入るため。ないと管理者ログインのクッキーが安全に設定されない
管理画面が S3 の写真を表示できるよう許可既定の設定は自分のアドレスの画像しか許可しない
DB 接続の暗号化 + 相手の確認本番 DB は暗号化されていない接続を拒否する。AWS 公式証明書をイメージに入れて「本物の AWS の DB か」を確認する

全体: apps/cms/config/env/production/、apps/cms/src/middlewares/cloudfront-proto.ts、apps/cms/Dockerfile。web はヘルスチェック用の /healthz だけ追加しました。

8. 初回デプロイと本番の初期設定

この章の変更を PR で上げてマージすると、デプロイが始まります。

deploy が終わると、ログの最後にサイトのアドレス(SiteUrl)、管理画面のアドレス(AdminUrl)、API トークンを入れるシークレット名などが出力されます。続けて3つのことを行います。

③を行う前は、サイトがエラー画面であるのが正常です(web が持つトークンがまだ仮のもので、Strapi が拒否するため)。デプロイの失敗ではありません。

① 管理者登録デプロイ直後すぐに最初にアクセスした人が最高管理者になるため
→
② データ入力03章と同じ方法本番 DB は空
→
③ API トークン発行 → 保管 → web 再起動web が新トークンを読むように

③は03章と同じ設定(Custom、読み取りのみ)で本番の Strapi から発行します。ローカルのトークンはローカルの DB にしかなく、本番では使えません。

実行場所: どこでも(AWS 認証情報のあるターミナル)

read -rs TOKEN   # トークンを貼り付け(画面・コマンド履歴に残らないように)
aws secretsmanager put-secret-value --secret-id <ApiTokenSecretName> --secret-string "$TOKEN"
aws ecs update-service --cluster <ClusterName> --service <WebServiceName> --force-new-deployment

ECS は秘密の値をコンテナ起動時にしか読まないので、web を再起動します。最初の1回の準備と後片付けを除けば、普段の運用中に人が AWS を直接操作するのはこの2行だけです(秘密の値はもともとコードの外で管理するものなので)。

9. デプロイが失敗したとき

失敗したデプロイは自動で以前の状態に戻るので、サイトはそのままです。本番を直接直さず、コードを直して同じ流れ(PR → マージ)で再度送ります。コードの問題ではなく一時的な失敗なら、Actions 画面でRe-runすれば構いません(同じコミットのイメージがすでにあればビルドは飛ばされます)。この資料を作る際も、初回デプロイで2回失敗しました。

症状(どこで見るか)原因
publish が Not authorized to perform sts:AssumeRoleWithWebIdentity(Actions のログ)ロールの条件と GitHub の身分証の形式が違う(4節)
deploy が Invalid rule description(CloudFormation コンソール → スタック → イベント)AWS に送った説明文に使えない文字(>)。AWS へ送る名前・説明は英語で
deploy が長時間かかったあと失敗(ECS コンソール → サービス → イベント・ログ)新しいコンテナがヘルスチェックを通過できない(設定値、DB 接続など)。CloudWatch Logs のアプリログを見る

10. 費用と後片付け

この構成は動かしているだけで料金がかかります(東京リージョン、2026-09 時点で概算月 $150、1日 $5)。大きい項目は DB(Aurora、約$55)、NAT Gateway(約$49)、コンテナ(約$27)、ALB(約$18)です。

消す方法(アプリ → データ → 土台の順)省略可

実行場所: リポジトリのルート(AWS 認証情報のあるターミナル)

pnpm -F infra exec cdk destroy ThreeTierApp -c imageTag=-
# データスタックは削除保護を解除してから消す(DB は最後のスナップショットが残る)
aws cloudformation update-termination-protection --no-enable-termination-protection --stack-name ThreeTierData
pnpm -F infra exec cdk destroy ThreeTierData -c imageTag=-
pnpm -F infra foundation destroy -c githubSubjectPrefix=-

残った DB スナップショットが不要なら RDS コンソールで消します。
