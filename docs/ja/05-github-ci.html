PR を作ると検査が自動で走り、すべて通過しないと main にマージできないリポジトリを作る。

1. CI とは

CI(Continuous Integration、継続的インテグレーション)は、変更を main に取り込む前に、決まった検査を人ではなく機械が毎回同じ方法で実行することです。

新メニューを店に出す前に、毎回同じチェックリストで検品するのと同じです。「味は見たはず」と信じる代わりに、チェックリストを通過したものだけをメニューに載せます。
この章でやることやらないこと(必要なら追加)
コードの形・よくあるミス、型、秘密の値の漏えい、本番用イメージのビルド、イメージの脆弱性自動テスト(単体・画面操作)、性能測定など。この例は読み取りだけの単純な画面なので入れていません

2. GitHub に上げて最初の PR を作る

GitHub で空のリポジトリを作り(README などは追加しない)、01〜04章のコミットを上げます。それ以降はブランチを作って PR で取り込みます。

実行場所: リポジトリのルート

git remote add origin https://github.com/<owner>/<repo>.git
git push -u origin main              # 01〜04章のコミット(main の保護を有効にする前に)

git switch -c ci/setup               # この章の作業はブランチで
# … 3〜5節のファイルを追加 …
git add . && git commit -m "ci: lefthook・Dockerfile・GitHub Actions の CI を追加"
git push -u origin ci/setup          # → GitHub の画面で「Compare & pull request」から PR を作成

PR を作ると、CI が初めて動きます。一度動いたあとで、7節のリポジトリ設定(main の保護)を有効にします。検査名が一度登録されないと、必須検査として選べないためです。

3. 3重の検査

作業は main ではなくブランチ(作業用のコピー)で行い、PR(Pull Request、「この変更を main に取り込んでください」という申請)でまとめます。

手前ほど早く教えてくれて、奥ほど飛ばせません。だから同じ検査を複数の場所に置きます。

4. コミット直前: lefthook

git commit を押した瞬間に、自分の PC で自動的に動く検査です。ルールはリポジトリの lefthook.yml にあり、pnpm install のときに各自の PC にインストールされるので、チーム全員が同じ検査を通ります。

実行場所: リポジトリのルート

pnpm add -Dw lefthook

そして pnpm-workspace.yaml の allowBuilds に lefthook: true と書きます。01章で「インストール時のスクリプト実行を禁止する」と説明しましたが、lefthook はインストール時に git へ検査を登録するスクリプトが必要なので、これだけ許可します。

検査やること
gen-types (07章のあとに追加)Strapi のスキーマファイルがコミットに含まれていれば、画面用の型を作り直して一緒にコミット(04章の pnpm gen:types を自動で。DB が起動している必要がある)
biomeコミットするファイルのコードの形を直し、よくあるミスを見つける
gitleaksパスワード・トークンのような文字列があればコミット自体を止める

hook は飛ばすこともでき(--no-verify)、インストールしていない人には効きません。だから同じ検査を CI でもう一度行います。hook は早い通知、CI は強制です。

5. PR のたびに: GitHub Actions

.github/workflows/ci.yml に書いておくと、GitHub が PR のたびにランナー(GitHub が用意する新しい仮想マシン)で検査を実行します。ランナーは毎回新しく作られるので、「自分の PC では動くのに」が通用しません。

検査名やること防いでくれるもの
checkBiome、型検査、インフラコード(CDK)の変換確認 (CDK は06章で追加)ミス・タイプミス、自分の PC でしか動かないコード
secretsgitleaks ですべてのコミット履歴を検査過去のコミットに混ざった秘密の値
image (web) / image (cms)本番と同じ Docker イメージをビルドし、Trivy で脆弱性を検査壊れたビルド、イメージ内の既知の脆弱性
ワークフローで守っている2つのセキュリティ原則 省略可
原則なぜ
他人が作ったアクションはバージョン名(@v7)ではなくコミット SHA で固定バージョン名は別のコードに差し替えられることがあります。2026年3月、実際に有名なアクションが悪意あるコードに差し替えられ、多くの CI で秘密の値が漏えいしました
CI に与える権限は既定で読み取りだけ(permissions: contents: read)。検査結果のアップロードに必要な書き込みだけをその job に追加アクションが悪意あるものでも、リポジトリを書き換えられません

6. Docker イメージと脆弱性検査

06章では画面と CMS をDocker イメージ(アプリと実行に必要なものをまとめた箱)として AWS で動かします。CI は PR のたびにそのイメージを同じようにビルドしてみて、中の部品に既知の脆弱性がないかTrivyで検査します。レシピは apps/web/Dockerfile、apps/cms/Dockerfile です。

2段階で作る

1段階目でインストール・ビルド、2段階目には実行に必要な成果物だけを移す。ビルド道具は本番イメージに入らない

不要なものは入れない

ないものは攻撃に使われることも、脆弱性として見つかることもない

root ではないユーザーで実行

コンテナが破られても被害が小さい

秘密の値は入れない

実行時に環境変数として渡す(06章)。.dockerignore で .env も除外する

脆弱性が見つかったとき 省略可

イメージには自分で選んでいない部品が数千個入っており、新しい脆弱性は毎日公開されます。この資料を作る際も、最初に何件か見つかりました。対応の順序は、①修正版があれば上げる(pnpm-workspace.yaml の overrides)→②実行に使っていなければイメージから外す→③どちらもできなければ理由と期限を書いて例外にする、です。

Security タブの Code scanning 省略可

CI は Trivy の結果を SARIF(検査結果の標準形式)として GitHub に上げます。Code scanning は検査ツールではなく、上がってきた結果を警告一覧として保管し、「いつ発生していつ直ったか」を追跡する機能です。使えないプランなら、結果アップロードの手順だけ外せば構いません。

7. リポジトリ設定: 「通過しないと取り込めないように」

CI は結果(✓/✗)を表示するだけです。強制するのはリポジトリ設定です。CI が一度動いたあとで設定します。

マージ方式: squash のみ

Settings → General → Pull Requests。PR の中の複数のコミットを、main に1つのコミットとしてまとめます。PR のタイトルが main のコミットメッセージになるので、履歴がすっきりします。

Ruleset: main の保護

Settings → Rules → Rulesets → New branch rulesetで main を対象に作ります。

ルール効果
Require a pull request before mergingmain への直接 push を禁止。必ず PR を経由する
Require status checks to pass5節の検査4つが ✓ でないとマージ不可
Block force pushes / Restrict deletionsmain の履歴の上書き・削除を禁止
この章の設定はpublic リポジトリを前提にしています。private リポジトリでは GitHub のプランによって Ruleset、Secret scanning、Code scanning が使えないことがあります。会社のリポジトリで使える機能を先に確認してください。
