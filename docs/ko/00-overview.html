CHAPTER 00

전체 구조와 도구: 무엇을, 무엇으로, 왜 만드나

본격적인 실습 전에 완성된 모습과 흐름을 먼저 봅니다. 이 장만 읽어도 "지금 어디쯤을 하고 있는지" 알 수 있습니다.

1. 이번 실습의 목표

여러분은 이미 3층 아키텍처(웹 → 앱 → DB)의 인프라를 설계했습니다. 이번에는 그 인프라 위에 올라갈 애플리케이션을 직접 개발하고, GitHub를 통해 자동으로 배포하는 흐름을 체험합니다.

  • WordPress에서는 "화면·관리자·DB 연결"이 한 덩어리의 블랙박스였습니다.
  • 이번에는 그 덩어리를 화면(Next.js)과 관리 도구·API(Strapi)로 나누고, 둘이 어떻게 통신하는지 직접 만들어 봅니다.

이 자료에서는 예로 キム系 라멘 가게 「麺屋ヤマモリ」의 메뉴 사이트를 만듭니다. 가게 직원이 관리자 화면에서 메뉴와 가격을 입력하면, 손님이 보는 사이트에 그대로 반영됩니다.

이 자료의 사용법: 이 자료는 "똑같이 따라 만드는 정답"이 아니라 "이런 방식으로 개발하고 배포한다"는 참고 예시입니다. 명령과 설정은 그대로 재현할 수 있게 적었지만, 여러분은 자신이 만들고 싶은 사이트(주제·데이터·화면)로 바꿔서 만들어 보세요. 라멘 가게의 데이터나 사진은 제공하지 않습니다. 예시 값은 참고만 하고, 여러분의 것을 준비하세요.

2. 완성된 모습 (AWS)

손님이 메뉴 페이지를 열면 일어나는 일

  1. 브라우저가 CloudFront(AWS의 입구)에 접속합니다. HTTPS 암호화도 여기서 처리합니다.
  2. CloudFront가 VPC 안의 ALB(부하 분산기)로 요청을 넘깁니다. ALB는 인터넷에 직접 공개되어 있지 않습니다.
  3. ALB가 요청을 Next.js(화면 담당 서버)로 보냅니다.
  4. Next.js가 API 토큰을 들고 Strapi에 "메뉴 목록 주세요"라고 요청합니다. 이 통신은 VPC 내부에서만 일어나고, 토큰은 브라우저에 절대 전달되지 않습니다.
  5. Strapi가 Aurora(DB)에서 메뉴 데이터를 읽어 JSON으로 돌려줍니다.
  6. 사진은 S3에 저장되어 있습니다. Next.js가 완성된 HTML을 만들어 손님에게 돌려줍니다.

3층 아키텍처와의 대응

층역할이번 구성
1층 웹요청을 받는 입구CloudFront + ALB
2층 앱화면을 만들고 데이터를 처리Next.js와 Strapi (2개로 분리)
3층 데이터데이터와 파일을 저장Aurora PostgreSQL + S3
왜 앱을 2개(Next.js와 Strapi)로 나누나요?
  • 역할 분리: 화면 디자인을 바꿔도 CMS는 그대로, CMS를 업데이트해도 화면은 그대로 둘 수 있습니다.
  • 보안: Strapi의 API 토큰을 Next.js 서버 안에만 두면, 브라우저에서는 절대 볼 수 없습니다.
  • 재사용: 같은 Strapi API를 나중에 스마트폰 앱이나 다른 사이트에서도 쓸 수 있습니다. 이런 구조를 헤드리스 CMS라고 합니다.

인프라 관점에서는 "앱 서버가 1종류에서 2종류가 되는 것"뿐입니다. 여러분이 설계한 구조에 서비스(또는 서버)를 하나 더 두면 됩니다.

여러분이 설계한 구조(WordPress 기준)와 다른 점

여러분은 WordPress를 올리는 것을 전제로 인프라를 설계했습니다. 이번 구성은 앱이 2개로 나뉘기 때문에 몇 군데가 다릅니다. 3층 구조 자체는 같으므로, 아래 차이만 반영하면 여러분의 설계 위에서 그대로 동작합니다.

항목WordPress 기준 설계이번 구성여러분의 구조에 적용하려면
앱 서버WordPress 1종류Next.js + Strapi 2종류ECS라면 서비스를 하나 추가합니다. EC2라면 같은 서버에 둘 다 띄워도 됩니다

앱끼리의 통신없음 (한 덩어리)Next.js → Strapi보안 그룹에서 Next.js → Strapi(포트 1337) 통신을 허용합니다

이 자료의 AWS 구성은 정답이 아니라 한 가지 예입니다. 인프라는 여러분의 설계를 쓰고, 이 자료에서는 "그 위에 앱을 어떻게 개발하고 배포하는가"를 참고하세요.

3. 로컬 개발 환경 (내 PC)

개발은 내 PC에서 합니다. AWS와 같은 3층 구조를 PC 안에 작게 재현합니다.

4. 개발부터 배포까지의 흐름

  1. 로컬에서 개발: 스키마 추가, 화면 수정 등을 하고 내 PC에서 동작을 확인합니다.
  2. 브랜치에 push: main에 바로 넣지 않고 작업용 브랜치에 올립니다.
  3. Pull Request(PR): "이 변경을 반영해 주세요"라는 요청입니다. 이때 CI(자동 검사: 코드 형식, 빌드, 시크릿 유출 검사 등)가 자동으로 돕니다.
  4. 리뷰 후 머지: 검사를 통과하고 리뷰가 끝나면 main에 합칩니다.
  5. 자동 배포(CD): main이 바뀌면 GitHub Actions가 AWS에 배포합니다. 사람이 AWS 콘솔을 만질 필요가 없습니다.

5. 코드로 하는 일, 화면으로 하는 일

Strapi를 쓰면 처음에 기본 설정만 코드로 해 두면, 그 뒤의 데이터 작업은 관리자 화면에서 끝납니다. 코드를 고쳐야 하는 곳은 아래로 정해져 있습니다.

🧑‍💻 코드로 하는 일

· 저장소 뼈대, DB 컨테이너 (01장)
· Strapi 설치 시 DB 연결 설정 (자동 생성)
· Next.js 화면 (04장). 화면은 코드로 만듭니다
· 배포 준비 (06장): 사진을 S3에 저장하는 설정(config/plugins.ts), S3 사진 표시 허용(config/middlewares.ts), Dockerfile
· CI/CD 설정 (05·06장)

🖱️ Strapi 관리자 화면에서 하는 일

· 데이터 구조(스키마) 설계. 로컬에서만 합니다 (02장)
· 데이터 입력, 수정, 공개 (03장)
· API 토큰 발급과 권한 (03장)
· 사진 업로드

화면에서 데이터 구조를 저장하면 Strapi가 설계도 파일(schema.json)을 자동으로 만듭니다. 이 파일은 코드와 똑같이 Git으로 운영에 배포됩니다. 즉 "직접 코드를 쓰지는 않지만, 결과는 코드로 관리된다"는 구조입니다.

6. 사용하는 도구

Next.js

React 기반 웹 프레임워크. 서버에서 HTML을 만들 수 있어서, 토큰 같은 비밀을 서버에만 둘 수 있습니다.

Strapi

오픈소스 헤드리스 CMS. 관리자 화면에서 데이터 구조를 만들면 API가 자동으로 생깁니다.

PostgreSQL

관계형 DB. 로컬에서는 Docker로, AWS에서는 Aurora로 실행합니다.

Docker

프로그램을 "컨테이너"라는 상자에 담아 어디서든 똑같이 실행하는 도구입니다.

pnpm

Node.js 패키지 관리자. 여러 앱을 저장소 하나에서 관리(모노레포)할 수 있습니다.

Biome

코드 형식 통일과 실수 검출을 한 번에 하는 도구입니다.

GitHub / Actions

코드 보관과 리뷰, 그리고 자동 검사와 자동 배포를 담당합니다.

AWS CDK

AWS 구성을 TypeScript 코드로 적는 도구입니다. 코드에서 구성이 만들어집니다.
