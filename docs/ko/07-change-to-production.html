CHAPTER 07

변경을 운영까지: 작은 기능 하나를 끝까지 보내기

지금까지 만든 흐름을 처음부터 끝까지 한 번 돌려 봅니다. 로컬에서 작은 기능을 추가하고, PR을 만들어 머지하면 나머지는 자동으로 운영에 반영됩니다. 마지막으로 "무엇이 코드로 배포되고, 무엇은 운영에서 손으로 하는가"를 다시 확인합니다.

추가 메뉴에 "売り切れ(품절)" 표시를 추가하고, 로컬 → PR → CI → 머지 → 자동 배포 → 운영 관리자 화면에서 켜기까지 마친다.

1. 무엇을 바꾸나

직원이 관리자 화면에서 "품절"을 켜면, 사이트의 추가 메뉴가 흐려지고 "売り切れ"가 붙게 합니다. 필드 1개와 화면 몇 줄로 끝나는 작은 변경이지만, 스키마·타입·화면·배포·운영 데이터가 모두 한 번씩 등장합니다.

바뀌는 것누가 바꾸나운영에 가는 방법
apps/cms/src/api/extra/content-types/extra/schema.json (스키마)로컬 관리자 화면 → Strapi 가 파일로 씀Git → PR → 머지 → 자동 배포
apps/web/src/types/strapi.d.ts (타입)pnpm gen:types
apps/web/src/app/page.tsx (화면)사람이 코드로
"チャーシュー 는 품절" (데이터)운영 관리자 화면배포되지 않음. 운영에서 직접

2. 로컬: 스키마에 필드 추가

실행 위치: 저장소 루트 (작업 브랜치에서)

git switch -c feat/extra-sold-out
pnpm dev:db
pnpm dev:cms

02장과 같은 방법으로 Content-Type Builder → Extra → Add another field → Boolean을 고르고, 이름은 soldOut, ADVANCED SETTINGS의 Default value는 false로 합니다. Finish → Save.

Strapi가 설계도 파일에 필드를 추가합니다.

apps/cms/src/api/extra/content-types/extra/schema.json

  "menus": {
    "type": "relation",
    "relation": "manyToMany",
    "target": "api::menu.menu",
    "mappedBy": "extras"
  },
  "soldOut": {
    "type": "boolean",
    "default": false
  }
}
로컬 Strapi(pnpm dev:cms)를 켠 채로 브랜치를 바꾸지 마세요. 개발 모드의 Strapi는 파일이 바뀌면 다시 시작하면서 DB를 그 스키마에 맞춥니다. 필드가 없는 브랜치로 바꾸면 그 열을 지우므로, 입력해 둔 값이 사라집니다(이 자료를 만들 때 실제로 겪었습니다). 브랜치를 바꿀 때는 먼저 Strapi를 멈춥니다.

3. 타입 다시 만들기

스키마를 바꿨으니 web이 쓰는 타입도 다시 만듭니다(04장).

실행 위치: 저장소 루트 (Strapi 실행 중)

pnpm gen:types

apps/web/src/types/strapi.d.ts

/**
 * @description A boolean field
 * @default false
 */
soldOut: boolean | null;

boolean | null인 이유: 필드를 추가하기 전에 만든 데이터는 값이 비어 있습니다(null). 기본값 false는 새로 만드는 데이터에만 들어갑니다. 화면에서는 null을 "품절 아님"으로 다룹니다.

이 명령을 잊으면 화면 코드의 extra.soldOut이 타입에 없어서 타입 검사가 실패합니다. 내 PC에서 놓쳐도 PR의 CI(check)가 막아 줍니다.

4. 화면: 받아 온 값으로 표시를 바꾼다

아래는 디자인 설정을 뺀 요약입니다. 실제 코드는 apps/web/src/app/page.tsx의 추가 메뉴 부분입니다.

{extras.map((extra) => (
  <li>
    <div className={extra.soldOut ? "흐리게" : undefined}>   // 품절이면 사진을 흐리게
      <Photo media={extra.photo} />
    </div>
    {extra.soldOut && <span>売り切れ</span>}              // 품절일 때만 표시
    <p>{extra.name} +{yen(extra.price)}</p>
  </li>
))}

데이터를 가져오는 코드(lib/menu.ts)는 고치지 않습니다. 추가 메뉴는 이미 모든 글자·숫자 필드를 받아 오고 있어서, 새 필드도 그대로 들어옵니다.

5. 로컬에서 확인

실행 위치: 저장소 루트 (다른 터미널)

pnpm dev:web

로컬 관리자 화면의 Content Manager → Extra → チャーシュー에서 soldOut을 TRUE로 바꾸고 Publish합니다. http://localhost:3000을 새로고침합니다.

6. 커밋 → PR → 머지

실행 위치: 저장소 루트

pnpm lint
pnpm typecheck
git add apps
git commit -m "feat: 追加メニューに「売り切れ」表示を追加"
git push -u origin feat/extra-sold-out

커밋할 때 lefthook이 Biome으로 파일 모양을 정리합니다(Strapi가 다시 쓴 JSON의 들여쓰기도 원래대로). GitHub에서 PR을 만들면 CI 4개(check, secrets, image ×2)가 돌고, 모두 통과하면 squash 머지합니다(05장).

7. 자동 배포

머지하면 06장의 배포 워크플로가 스스로 시작합니다. 사람이 할 일은 없습니다.

단계이번 변경에서 일어나는 일
publishweb·cms 이미지를 새 커밋 SHA로 빌드 → Trivy 검사 → ECR
deployData 스택은 바뀐 것이 없어 그대로. App 스택은 두 서비스의 이미지 태그만 바뀜
ECS새 컨테이너가 뜬 뒤 옛 컨테이너를 내림(무중단). cms는 시작하면서 새 스키마를 보고 운영 DB에 sold_out 열을 추가

배포가 끝난 직후 운영 사이트를 열면 아무것도 바뀌지 않은 것처럼 보입니다. 운영 DB의 기존 데이터에는 품절 값이 비어 있기 때문입니다.

8. 운영에서 켜기

운영 관리자 화면(06장의 AdminUrl)에서 로컬과 같은 조작을 합니다: Content Manager → Extra → チャーシュー → soldOut TRUE → Publish. 운영 사이트를 새로고침하면 1절의 "변경 후" 화면이 됩니다. 품절이 풀리면 FALSE로 되돌리면 되고, 이것은 배포 없이 바로 반영됩니다.

스키마는 배포되고, 데이터는 배포되지 않는다. 필드(그릇)는 코드로 운영에 갔지만, "무엇이 품절인가"(데이터)는 로컬에서 켜 둔 것이 운영으로 가지 않습니다. 가게의 품절처럼 날마다 바뀌는 것은 데이터로, 표시 방법처럼 한 번 정하면 되는 것은 코드로 둡니다.

9. 전체를 돌아보며

이 장에서 한 일은 00장에서 그린 흐름 그대로입니다.

장이번 변경에서 쓰인 것
01 로컬 환경pnpm dev:db / dev:cms / dev:web
02 스키마Content-Type Builder로 필드 추가 → schema.json
03 데이터관리자 화면에서 값 입력·Publish (로컬과 운영에서 각각)
04 화면pnpm gen:types, 받아 온 값으로 표시 바꾸기
05 CI커밋 전 lefthook, PR의 검사 4개, squash 머지
06 CD머지 → 이미지 한 번 빌드 → 자동 배포 → 무중단 교체

여러분의 사이트에서도 같습니다. 기능을 바꿀 때마다 로컬에서 만들고 확인 → PR → 머지만 하면 운영까지 갑니다. 운영에서 사람이 하는 일은 데이터를 입력하는 것뿐입니다.
