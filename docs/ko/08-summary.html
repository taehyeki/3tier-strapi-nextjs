3. 장별로 한 일

장한 일기억할 한 가지
00 전체 구조완성된 모습과 흐름프론트·백엔드·DB는 가게의 홀·주방·창고
01 로컬 환경저장소 하나에 화면·CMS, DB는 컨테이너설정 값은 환경변수로. 로컬과 운영은 넣는 곳만 다르다
02 스키마데이터의 그릇 설계하나뿐? 여러 개? 붙어 있나, 공유하나?
03 데이터·API입력·공개, API 토큰API는 처음에 잠겨 있다. 토큰은 읽기만 허용
04 화면서버에서 데이터를 가져와 표시토큰은 서버에만. 타입은 스키마에서 자동 생성
05 CI커밋 직전·PR마다 자동 검사, main 보호검사를 통과한 코드만 main에 들어간다
06 CD·배포머지하면 AWS에 자동 배포, 운영 초기 설정이미지는 한 번 만들고 그대로 배포. GitHub에 비밀 값을 두지 않는다
07 변경을 운영까지작은 기능 하나를 처음부터 끝까지스키마는 배포되고, 데이터는 배포되지 않는다

5. 어디에나 통하는 원칙 다섯 가지

비밀 값은 코드 밖에

로컬은 .env(Git 제외), 운영은 Secrets Manager. 코드·이미지·GitHub에 남기지 않는다

출입증은 서버에만

API 토큰은 화면을 만드는 서버만 갖는다. 브라우저에는 결과(HTML)만

권한은 필요한 만큼만

토큰은 읽기만, CI는 읽기만, GitHub의 AWS 역할은 할 일 하나만

검사를 통과한 것만 main에

사람의 기억이 아니라 기계의 검사와 저장소 규칙으로 지킨다

같은 코드를 모든 환경에서

로컬과 운영은 코드가 같고, 환경변수로 넣는 값만 다르다

6. 여러분이 할 일

여기까지 라멘 가게를 예로 개발부터 운영 배포까지의 전체 과정을 살펴보았습니다. 이제 이것을 참고해, 여러분이 구상한 인프라를 바탕으로 자신만의 CMS 사이트를 개발해 주세요.

  1. 주제를 정하고 "화면에 보여 줄 정보"를 적는다 → 3가지 질문으로 그릇을 고른다(02장)
  2. 로컬 환경을 만든다: 저장소 하나에 화면·CMS, DB는 컨테이너(01장). 여러분의 설계가 MySQL이면 Strapi를 MySQL로 만들어도 됩니다
  3. 스키마 → 데이터 → 토큰(02·03장)
  4. 화면을 만든다: 받아 온 값을 어디에 넣을지부터(04장). 디자인은 자유
  5. GitHub와 CI를 붙인다(05장). 회사 저장소에서 쓸 수 있는 기능을 먼저 확인
  6. 여러분의 인프라에 배포한다(06장). 00장의 "WordPress 기준 설계와 다른 점" 표를 보고 설계에 반영합니다: 앱 2개, 입구의 분배, 앱끼리의 통신, 사진은 S3
  7. 작은 변경을 운영까지 보내 본다(07장). 흐름이 한 바퀴 돌면 완성입니다
막히면 이 저장소를 보세요. 문서에 나온 설정은 모두 실제로 동작한 파일 그대로입니다: 화면 apps/web/, CMS apps/cms/, 자동 검사 lefthook.yml·.github/workflows/ci.yml, 자동 배포 .github/workflows/deploy.yml, AWS 구성 infra/.
